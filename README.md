Some scripts put in the clipboard a prompt to give to an LLM. They are in the `step by step` folder.

`run.bat`, in the root, is the entry point. It starts `0_run_all`, which runs them all in a single terminal: after each script, it says what to paste and copy, waits, then runs the right next script. Its question is a line of signs: where to paste the prompt (🆕 NEW chat, or 🔁 SAME chat after an error of the csv), what to copy from the answer of the LLM (📄 copy WHOLE answer, or 📊 copy CSV only), then what each key does (⏎ Enter, y after ✅ when the LLM says it is correct, and y after 🏁 when the review finds no problem in the menu, which saves it). ? explains it in a whole sentence. Typing the number of a script (2.5, ...) jumps to it, c copies the prompt again, w tells whether the clipboard still holds the prompt (nothing was copied since) or something else, which may be the answer of the LLM, q quits. It remembers where the user is: closed and started again, it asks the same question again. It keeps a history file for each menu, in the DB/history folder, named after the date and the time its first script (0. or 1.) was started at. A menu has one file only: script 0. or 1. that is run again after itself (an error, other options), and script 0. that is run after the LLM added foods to the pool (script 0.5) or gave limits (script 6.5), go on in the same file, even when `run.bat` was closed in between. Starting script 0. or 1. from any other script starts a new menu, and so a new file. The file has all that was printed in the terminal and typed there, each prompt given, and each answer of the LLM that a script read from the clipboard, in the order they happened. A prompt is between a `<<<< PROMPT` line and a `>>>> END OF THE PROMPT` line, an answer between `<<<< ANSWER OF THE LLM` and `>>>> END OF THE ANSWER OF THE LLM`. Both lines tell the date and the time. An answer the user did not copy (the LLM says it is correct, and y is typed) is not there. The history also tells the version of the scripts that are run, at the start of a menu, each time `run.bat` is started, and before a script when it changed since: the commit of git, whether the scripts were changed since it, and the date and the time the last one was changed at. The history file of a menu that is added to successful_menus.csv is renamed `menu N.txt`, for the menu N, when the user types y after its review, and goes on under this name: a menu has so one file, which shows every prompt and every answer that led to it, with its reviews and what they corrected. A file named after a date is the one of a menu that was never added. `menus.bat` tells the file of each menu it lists. The folder is not in git: the prompts tell the address.

A menu is made in one of two ways. Script 0. computes it from the food pool: the foods the user is willing to buy and eat (DB/food_pool.csv), each one with the most of it in a day (DB/food_limit.csv). No LLM chooses its amounts, nor its foods unless the menu must differ from the saved ones: it only adds foods to the pool, writes the text of the menu and reviews it. Script 1. asks the LLM to write a menu, whose foods then have to be identified (scripts 2. to 4.). Both ways go on with the products (script 5.) and the report (script 6.). Enter starts with script 0.

0. `0.0_get_menu_from_pool`: asks the options of the menu, as script 1. does, then computes the cheapest menu of the foods of the pool whose total of the day is between min and max for each nutrient of the daily nutrient needs table. A food is counted as its product, as in the report, and at the price of its product: a food without price is counted at the price of the half of the foods of its unit, and is marked. A food that is in the menu has at least its min, or else a tenth of its max, and at most its max. Each food of the menu costs 0.1 euro more than its price, so that a menu of few foods is preferred. The foods the menu must have are in it, the ones it must not have are left out. The same pool gives the same menu: when there are saved menus, the script asks whether the menu must differ from them. It then gives a prompt for the LLM to choose the foods of the menu, not their amounts: the prompt contains the daily nutrient needs table, the goals and tips of the user, the foods and amounts of every menu of successful_menus.csv, the pool and food_manual.csv, and asks for 12 to 20 foods of other food families than the ones of those menus (other main sources of protein, other grains, other vegetables and fruits), from the pool or not, the water, the salt and the supplements being allowed to be the same. The LLM writes them as the foods of the pool are written, script 0.5 saves them in DB/menu_foods.csv, and script 0., run again, asks whether to compute the menu from them only (n computes it from the whole pool again, and forgets them). The foods the menu must have are counted with them. The file is removed when the menu is taken. The first time, the pool is made of the foods of the menus of successful_menus.csv, the max of each one being its largest amount in them: both files are edited as the user wishes, a food without max being left out. If a menu is found, the script shows it with its price, and asks whether to take it: it is then saved in menu.csv, without text, and the user goes to script 5. Otherwise, or if the user asks for it, it gives a prompt to get other foods for the pool: the prompt contains the daily nutrient needs table, the goals and tips of the user, the pool and food_manual.csv, and tells the needs that no menu of the pool satisfies, with what the closest menu reaches for each one. The LLM writes each food with its description, its fdc_id and fdc_description in SR Legacy 2018 or in food_manual.csv, and its max. When the menu is computed from the foods the LLM chose, this prompt only shows those foods as the pool, contains the saved menus too, and asks not to propose their foods.
0.5. `0.5_copy_pool`: from the copied food list, the script checks each fdc_description against the csv files, as script 2.5 does, then adds the foods to the pool and their max to food_limit.csv. When the list answers the prompt that asks for the foods of a menu that differs from the saved ones, or adds foods for such a menu, its foods are also saved in DB/menu_foods.csv, and a food that already has a max keeps it. The user goes back to script 0., which computes the menu again: run by `run.bat` right after script 0.5, it does not ask the options again.
1. `1.0_get_menu_prompt`: gives a prompt to get a vegan menu that satisfies all the daily nutrient needs in the table. The prompt contains the daily nutrient needs table, the goals and tips of the user (DB/menu_tips.txt, a free text to edit, left out when the file is empty or missing), which the menu must follow, and food_manual.csv when it has foods, so that the menu takes them, written with their exact description, rather than new foods that would need ingredients and nutrients (scripts 3. to 4.). The script first asks in the terminal the options of the menu, each one answered by y or n: tell the LLM where the user lives, the menu must be as cheap as possible, as environmentally friendly as possible, as quick to prepare as possible, then a free text for anything else. Enter keeps the last answer. It then asks the foods the menu must have, and the ones it must not have: each one is typed as its fdc_id then its description (`172430 Peanuts, all types, raw`), and is only added when the description is the one of this ID in food.csv or in food_manual.csv. Otherwise the script tells the real description of the ID and the closest foods to the one typed. The foods answered last are kept, - removes them all. The prompt only tells the chosen ones, and so do the prompts that correct the menu (scripts 1.5 and 6). It last asks the changes of the daily nutrient needs table: one is typed as the whole row of the csv of the table, with its id, its name, and its new min and max (`1079,"Fiber, total dietary",30,85`), an empty max being no limit. It is only taken when the name is the one of this id in the table. daily_need_table.csv itself is not changed: while a change is chosen, every script (the prompts, the report of script 6.) takes its min and max instead of those of its row. Each change made before is asked again at each start of script 1., answered by y or n, Enter keeping the last answer: with n the row is the one of the table again, and the change is still asked the next time. - removes them all, and a row typed as the table has it loses its change. The answers, those foods, those changes and the address are in DB/menu_options.json, which is not in git: the address is changed there.
1.5. `1.5_copy_menu_then_check`: from the copied answer (the menu as a text, then its csv), the script saves the csv in menu.csv and the text in menu_description.txt, then gives a prompt to correct the menu (except when the csv is menu.csv as it is, with all its foods identified: only the text was written again, so the script saves it, says so, and the user goes to script 6.), and to check its foods against the ones it must have and must not have, and to spot any inconsistency between the text and the csv. The prompt contains the daily nutrient needs table, the menu as a text and the menu. The script itself refuses a menu that lacks a food it must have, which the LLM writes with its exact description and which gets its ID there, or that has a food it must not have under its exact description: under another one, script 2.5 warns about it once the food is identified.
2. `2.0_get_food_prompt`: gives a prompt to identify each food of the menu in food.csv from the SR Legacy 2018 from fdc.nal.usda.gov, or in food_manual.csv. The prompt contains the menu and food_manual.csv. The LLM writes one row per food of the menu, with the columns description, fdc_id and fdc_description (the description from USDA, to check if they correspond). A food that is in none of the two csv files has `new` as fdc_id. If every food of the menu already has its ID (a menu whose amounts or text alone were corrected), it says so, and the user goes to script 3.
2.5. `2.5_copy_foods_then_check`: from the copied food list, the script checks each fdc_description against the csv files, saves the IDs in menu.csv, then gives a prompt to correct the food list. The prompt contains the menu, the food list and food_manual.csv.
3. `3.0_get_ingr_prompt`: adds the foods marked `new` to food_manual.csv, and writes the new food list in new_food.csv: those foods, and every food of food_manual.csv that has no nutrient yet. Gives a prompt to get for each food of the new food list a list of ingredients. The prompt contains food_manual.csv and the new food list. If there is no new food, it says so, and the user goes to script 5.
3.5. `3.5_copy_ingr_then_check`: from the copied ingredient composition table, the script saves it in food_ingredient_manual.csv, then gives a prompt to correct it. If some of the ingredients are also food that are not in both csv files (`new` as ingredient_fdc_id), the script adds them in food_manual.csv and in the new food list, and the prompt asks for their ingredients. A food whose nutrients cannot be deduced from ingredients (a supplement, an isolate, ...) has `none` as only ingredient. The prompt contains the daily nutrient needs table, food_manual.csv, the new food list and the ingredient composition table. For each food in the new food list, the script deduces their nutrient composition from their ingredients, and updates food_nutrient_manual.csv.
4. `4.0_copy_nutr_if_given_then_check`: gives a prompt to correct the new rows in food_nutrient_manual.csv when the nutrient composition of a food can’t simply be the sum on all its ingredients. The prompt contains the daily nutrient needs table, the new food list, their ingredient composition and their nutrient composition. If the clipboard contains a nutrient table, the script first saves its rows in food_nutrient_manual.csv. The script checks if all nutrients from the daily nutrient needs table are present for each new food: the prompt asks for the missing ones.
5. `5.0_get_product_prompt`: gives a prompt to get, for each food of the menu that has no product yet, a real product the user can buy. The foods of the databases are generic ones: the product really bought may not have the same nutrients (a nutritional yeast is fortified with B12 or not). The prompt contains the daily nutrient needs table, the menu, and the nutrients the menu counts on each food for: the ones the food brings at least 20% of the total of the day of. The LLM writes two tables: the products (fdc_id, product, shop, price, package_amount, eco, source), then the nutrients that their label gives (product, nutrient_id, amount, source). If every food has a product, it says so, and the user goes to script 6. The products are not needed for the report: a food without product is counted as its generic food.
5.5. `5.5_copy_products`: from the copied answer, the script saves the products in product.csv and their nutrients in product_nutrient.csv. A product that its food already has (same description and same shop) is updated. Each food of the menu is counted as the product just given for it from now on (menu_product.csv). The product of a food that the menu does not have anymore stays there: a later menu that has this food counts it as this product again.
6. `6.0_get_report`: compares the menu with the daily nutrient needs table, each food being counted with the nutrients given for its product, or else with those of its generic food. It says the price of the day, from the prices of the products. If the table is satisfied, it says so, and gives the review prompt, which asks the LLM whether the menu has any risk or problem that the totals do not show (what is eaten together or apart, a food that blocks the absorption of a nutrient of another one, ...): if it has, the LLM writes the corrected menu, as a text then as a csv, which goes to script 1.5, and through the next scripts again. A menu is only added to successful_menus.csv once a review finds no problem in it: when the user types y at the question of `run.bat` that follows the review prompt. It is added with the options it was made with (the ones answered at script 1., without the address), the changes of the daily nutrient needs table it was made with (the needs column: the nutrient ids of each row, its min and its max, as in `1003:120:150`), the product of each food, and the date of this review (the reviewed column). The text of the menu is saved in the successful_menu_descriptions folder, in a file named after the number of the menu. Until then, the menu is only the one of menu.csv. A saved menu that is reviewed again from `menus.bat` and corrected is not added next to itself: once the corrected one is reviewed, it takes its place in successful_menus.csv, with its number, or only updates its text when the text alone changed. A menu that has no date in the reviewed column was saved before this rule, when a menu was added as soon as it satisfied the table. A review is a new discussion, and an LLM that is asked for problems always finds some, or undoes what the review before corrected: the prompt only asks for the serious ones (a harm for the health, a nutrient that is clearly not absorbed), and script 1.5 keeps what each review found (all that the LLM wrote before the menu, in DB/menu_reviews.json, which is not in git), so that the next review prompt tells it, says how many times the menu was reviewed, and asks not to tell those problems again nor to undo their corrections. Scripts 0. and 1. forget them when a new menu starts. The review prompt contains the daily nutrient needs table, the goals and tips of the user (DB/menu_tips.txt, a free text to edit, left out when the file is empty or missing), the menu as a text and the menu with its products. If the table is not satisfied, it first looks whether a product the user already has would make the menu satisfy the table when a food is counted as it instead, and offers to do so. If none does, it computes whether other amounts of the same foods satisfy the table: each food keeps between half and twice its amount, a supplement a whole number of doses, and the amounts chosen are the closest to the ones of the menu, changing as few foods as possible. If some do, it shows the amounts that change and offers to take them: menu.csv then has them, and the prompt asks the LLM whether each amount is realistic and safe to have every day. If they all are, the LLM writes the text of the menu again with them, without changing the csv: its answer goes to script 1.5, which only saves the text, then script 6. is run again and finds the table satisfied. If some are not, the LLM writes no menu but the limits of the foods at fault (description, min, max: the least and the most of the food in a day): its answer goes to script 6.5, then script 6. is run again and computes the amounts within them. A menu whose text does not have its amounts yet is not added to successful_menus.csv: script 6. asks for the text again. A menu that script 0. computed has no text: the same prompt asks whether its amounts are realistic, then for its text, the foods being spread over the meals of the day with the goals and tips of the user. When a menu is added to successful_menus.csv, its foods that the food pool does not have are added to it, each one with its amount as max when it has no limit. If no amounts do, or if the user refuses them, it gives a prompt that makes the LLM correct what is wrong, with the first of three corrections that can fix the menu, from the cheapest for the user to the most expensive:
    1. the numbers of the products: the prompt lists the numbers behind the lacks and excesses that the user did not read on the product, to check them. This correction is only there when there are such numbers.
    2. other products for the same foods, that suit this menu better.
    3. the menu itself.

    The prompt contains the daily nutrient needs table, the goals and tips of the user, which a correction of the menu must follow, the menu with its products, the lack of nutrients and the excess in nutrients, the products of the foods of the menu, and the foods that bring the nutrients in lack or in excess. When no amounts of the foods satisfy the table, it also contains the amounts that come the closest to it (menu_closest_amounts.csv) and names the needs that are still out of their range with them: the ones a product or a food must change for. The user copies the whole answer: `0_run_all` sees from its tables whether it corrects products, and runs script 5.5 then script 6. again, or the menu, and runs script 1.5, or gives limits of foods, and runs script 6.5 then script 6. again.

6.5. `6.5_copy_limits`: from the copied answer to the prompt of script 6. that asks whether the computed amounts are realistic, the script saves the limits of the foods the LLM refuses the amount of in food_limit.csv (fdc_id, description, min, max, in grams or in doses for a day, an empty one meaning no limit). A food of the answer must be one of the menu, with its description unchanged. The limits are kept for every menu, a new limit of a food replacing its old one: the file is edited to change or remove them. Script 6. brings an amount that is out of the limits of its food back within them before it judges the menu, and computes amounts within them only. After the limits are saved, `0_run_all` goes back to script 0. when the menu has no text yet (it was computed from the pool, and is computed again from it), to script 6. otherwise. The prompts that ask for a menu or correct it (scripts 1. and 6.) contain food_limit.csv when it has rows.

A product is one of the generic foods (fdc_id) as it is really sold. Its price is in euros for package_amount, which is in grams, or in doses for a supplement. Its eco level goes from A (the best) to E. Its source tells where the information comes from: the website the LLM read it on, `estimate` for what the LLM knows by itself, or `on site` for what the user read on the product. Each nutrient of a product has its own source. A menu is checked when each of its foods is a product whose information and nutrients were all read on site.

`menus.bat`, in the root, is the entry point to list the menus of successful_menus.csv. It starts `list_menus`, which first asks for the number of a menu, to show only that one. With Enter instead, it asks for each option whether the menus must have been made with it (y), or whether it does not matter (n), whether their foods must all be products read on site, and a text their other wishes must contain. It then shows the text and the foods of each menu that was made with all of them, with the changes of the daily nutrient needs table it was made with, the product each food was counted as, its price of the day, whether it is checked, and the date of the review that found no problem in it. Typing the number of one of those menus then asks what to put in the clipboard. With t, it is the menu to read: its text, then a markdown table of its foods, each one with its amount and all the information of its product (shop, price, package, price of the day, eco level, source and date), or with the food alone when it has no product. With c, it is the csv tables to give to an LLM: its foods with their ID, amount and product, the nutrients those foods are counted with (food ID, nutrient ID, name, unit, amount and source), only for the nutrients of the daily nutrient needs table, and its products. With r, it is the review prompt of script 6., with the wishes and the daily nutrient needs this menu was made with: the corrected menu the LLM may write is read by starting `run.bat` and typing 1.5, and takes the place of this menu once it satisfies the table and a review finds no problem in it.

`product.bat`, in the root, is the entry point to replace the product a food is counted as, for a product the user found in a shop. It starts `change_product`, which shows the products of product.csv with their IDs, and whether their food is counted as them. The product to replace is typed as its product_id, or as the start of its row (`17,4,Natura Force Vitamine D3 K2 végétale (gélules)`): its fdc_id and its description, when they are typed, must be the ones of this ID. When its food has other products, one of them can be chosen instead of a new one. Otherwise the script asks the columns of the new product (description, shop, price, package_amount, eco), Enter keeping the value of the product it replaces and - emptying it: its source is `on site` and its date the one of the day. A product with the same description in the same shop is the same product, whose row is updated: sold by another shop, it is another product, with its own price, and the one it replaces stays in product.csv. The script then asks its nutrients: k keeps the ones of the product it replaces, m shows them and lets the user type the ones that change (`1003,25`, its source being `on site`, or `1003,-` to take the one of the generic food again), l gives a prompt to ask an LLM for them, from what the label says (its text or a photo, pasted after the prompt), and reads the csv of the answer from the clipboard. The food is counted as the new product from now on (menu_product.csv), in the menu being made and in the next ones. Each menu of successful_menus.csv that has this food is then judged with it, with the daily nutrient needs it was made with: one that still satisfies them is counted with the new product from now on, stays reviewed, and the script tells its price of the day before and after. One that does not keeps its product until it is corrected: the first of them becomes the menu being made, with the wishes and the daily nutrient needs it was made with, and `run.bat`, with Enter, runs script 6. on it, which goes on as for any menu that does not satisfy the table. Once reviewed, the corrected menu takes its place. `run.bat` only makes one menu at a time: when another one is being made there, the script asks before giving it up, and the next menus to correct wait. `product.bat`, started again, tells the menus that are still to correct, and Enter instead of a product goes on with the next one. It also offers to count a menu with the products its foods are counted as now when it does not yet, and still satisfies its daily needs with them.

The prompts that ask for a menu (scripts 1., 1.5 and 6., and the review prompt) tell the LLM to write it as a text first, meal by meal, with the amount of each food, then as a csv: the user copies the whole answer, and the script takes as the text all that is written before the csv, from its first title (a line in bold or a markdown title of level 2 or more): the code an LLM ran and its intro, written before it, are left out.

The name of a script says what the user must copy before running it. The other scripts don’t look at what is in the clipboard.

When the prompt asks the LLM to go check the SR Legacy 2018 DB, it asks it to use its web search tool.

For the scripts 1.5, 2.5, 3.5 and 4., the user must run the script, paste the clipboard into the LLM, and if it says it is correct, go to the next script, otherwise copy the csv table it gives and do this again (run the script, paste, …).

The prompts tell the LLM to either say everything is correct, or write a table in the csv format easy to copy: the whole corrected table, except at script 4., where it only writes the rows to change or to add. The menu, daily nutrient needs table, new food list, etc… are in the csv format.

If the script finds an error, the prompt contains the error message and the user pastes it in the same discussion with the LLM. Otherwise, the given prompt is meant to be the start of a new discussion.

When the menu is corrected at script 6., a food whose description is unchanged keeps its ID: only the other ones are left to identify at script 2.

SR Legacy 2018 has no data for some nutrients (biotin, iodine, chromium, molybdenum, sulfur, and fluoride for most foods). At script 3.5, a nutrient that no ingredient of a food has data for is left out: script 4. asks the LLM for it. At script 6., a nutrient that at least half of the foods of the menu have no data for cannot be judged: it does not count as a lack.


This process allows the user to use its LLM subscription to the fullest instead of paying for API with a fully automatic solution. Here I use Gemini Pro.
